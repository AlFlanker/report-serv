# Сервис формирования отчётов

Angular 22 + **ng-zorro-antd**, Node.js 24, **PostgreSQL**, ExcelJS и **S3**.
Интерфейс соответствует предоставленным макетам «ЛК ЭБ · Формирование отчетов».
Обращения к БД целевых систем заменены подготовленными JSON-ответами.
PostgreSQL хранит задания, уведомления и метаданные; сформированные Excel находятся в S3.

## Локальная разработка

Требуются Node.js **24.15+ в ветке 24**, npm, Docker Engine и Docker Compose v2.

```bash
npm ci
npm run infra:up
npm start
```

`npm run infra:up` подготавливает локальные ключи и пароль БД в игнорируемом
`.env`, запускает **PostgreSQL 17** и **SeaweedFS 4.54**, инициализирует закрытый
бакет `reports`. Повторный запуск сохраняет существующие ключи и данные.
Настройка PostgreSQL дополняет существующий `.env`, сохраняя параметры S3 и
пользовательские поля. Необходимые поля описаны в [.env.example](.env.example).
Node автоматически читает `.env` при запуске приложения.

Интерфейс — порт **4200**, API — **3001**, S3 — **9000**, PostgreSQL — **5432**. Angular проксирует
`/api/**` на API. `npm start` запускает оба процесса приложения; Ctrl+C
останавливает их. PostgreSQL и S3 продолжают работать в Docker.

```bash
npm run build       # production-сборка интерфейса
npm run start:prod  # API и собранный интерфейс на одном порту 3001
npm run db:up       # только PostgreSQL
npm run s3:up       # только S3 и инициализация бакета
npm run s3:down     # остановка Compose; постоянные volumes сохраняются
```

Для изначально пустого кабинета с отдельной схемой PostgreSQL:

```bash
SEED_DEMO=false DATABASE_SCHEMA=empty_demo npm start
```

`SEED_DEMO` не очищает существующую БД. По умолчанию при первой инициализации
создаются шесть демонстрационных заданий №1043–1048. Их Excel также загружаются в S3.

## Всё приложение в Docker

```bash
npm run docker:up
```

Команда подготавливает локальную конфигурацию, собирает образ и запускает профиль
`app`: PostgreSQL и S3 → инициализация бакета → приложение. Готовый интерфейс и API доступны
на порту **3001**. Перед запуском освободите этот порт, остановив локальный API.
S3 и приложение публикуют порты только на loopback хоста. Приложение работает от
непривилегированного пользователя. Образы Node и SeaweedFS закреплены digest.

Данные сохраняются в volumes `s3-data` и `postgres-data`. Локальный API и
Docker-приложение по умолчанию используют одну БД и схему PostgreSQL. Одновременно
запускайте один backend на схему. Старый volume `app-data` сохранён в Compose для
восстановления прежней SQLite, но больше не подключается к приложению.
`docker compose down` сохраняет тома; `down -v` удаляет их вместе с данными.

```bash
npm run docker:build                       # только сборка
docker compose --profile app ps            # состояния контейнеров
docker compose --profile app logs app      # журнал приложения
```

В облачной среде с прокси сборка автоматически использует CA из
`BUILD_CA_CERT` или `CODEX_PROXY_CERT` как **BuildKit secret**. Проверка TLS
остаётся включённой; CA, `.env` и локальные ключи не попадают в слои образа.
В обычной среде дополнительный сертификат не требуется.

## Потоковая обработка

Путь данных:

```text
AsyncIterable строк → ExcelJS WorkbookWriter → ZIP → multipart upload → S3
```

- Каждая строка сразу фиксируется через `commit()`; общая таблица строк
  `sharedStrings` отключена. Нет `writeBuffer()`, полного буфера XLSX или
  промежуточного файла на диске.
- Потоки листов и ZIP ограничены буферами 64 КиБ. Ожидание `drain` передаёт
  backpressure до источника строк: медленный S3 останавливает чтение новых данных.
- По умолчанию размер части — **8 МиБ**, одновременно загружаются **2 части**.
  Память зависит от размера и числа частей, собираемой следующей части, буферов
  ZIP/SDK и размера отдельной строки, а не от полного размера отчёта.
- Сжатие ZIP уровня 1 уменьшает затраты CPU. Постоянные стили используются только
  для заголовков. На листе поддерживается до 1 048 575 строк данных плюс заголовок.
- Задание получает статус «Завершено» только после успешного завершения загрузки.
  Размер файла считается в потоке; количество строк — при записи.
- При отмене/ошибке останавливается источник строк и очищаются multipart-части.
  Уже отправленные PUT/COMPLETE ожидаются до завершения перед удалением объекта,
  чтобы поздний ответ не создал потерянный файл после очистки.
- Скачивание на сервере выполняется потоком S3 → HTTP с отменой чтения при
  отключении клиента. Существующий UI управляет скачиванием через браузерный Blob.

ExcelJS 4.4.0 внутри использует `StreamBuf`, который не обеспечивает нужный
backpressure. `BoundedWorkbookWriter` заменяет одну приватную точку `_openStream`
обычным ограниченным `PassThrough`. Версия ExcelJS закреплена; перед её обновлением
обязательно запускать тесты остановленного потребителя и чтения готового XLSX.

Фиксированные небольшие JSON-моки загружаются в память. Адаптер
`openReportData()` выдаёт строки лениво; для настоящей БД его можно заменить
асинхронным курсором, учитывающим `AbortSignal`. Генератор не собирает строки
курсорного источника в массив.

## Срок хранения, восстановление и миграция

Результат доступен 7 дней с момента завершения (настраивается). После истечения
API возвращает 410, обработчик удаляет объект из S3, сохраняя историю задания.
При ошибке удаления сохраняется намерение очистки в PostgreSQL и выполняется повтор.

Ключи содержат UUID конкретной схемы и отдельной попытки формирования, поэтому
разные установки и повторные запуски не перезаписывают результаты друг друга.
Префикс и бакет закрепляются за схемой;
замена бакета требует отдельного переноса объектов. Очередь переживает перезапуск;
прерванное задание возвращается в очередь. Ошибочные задания автоматически не повторяются.

Для обновления существующей установки остановите старый API и сохраните
резервную копию SQLite. Перенос выполняется отдельной командой **до первого
запуска нового приложения** в пустую целевую схему:

```bash
npm run infra:up
npm run db:migrate:sqlite -- --source .data/reports.sqlite
# Для второй независимой установки:
npm run db:migrate:sqlite -- --source /path/to/backup.sqlite --schema legacy_local
```

Переносятся номера и параметры заданий, статусы, уведомления, настройки,
метаданные S3 и очередь очистки. Существующие ключи объектов сохраняются.
Исходная SQLite открывается только для чтения и остаётся резервной копией.
Непустая целевая схема отклоняется; импорт выполняется транзакционно.
Если в старой версии ещё остались XLSX BLOB, мигратор загружает их в S3
порциями **64 КиБ**. Рабочее приложение больше не использует SQLite и не
содержит колонки для байтов Excel в PostgreSQL.

Инициализация бакета добавляет lifecycle-правило для префикса приложения:
незавершённые multipart-загрузки удаляются спустя сутки. Это резервная очистка
после жёсткого завершения процесса, когда программная отмена уже невозможна.
Приложение ведёт устойчивую очередь очистки завершённых объектов после сбоев.
Для внешнего S3 настройте аналогичное lifecycle-правило отдельно либо запустите
инициализатор с административными правами; обычному runtime менять правила не нужно.

## Конфигурация PostgreSQL

| Переменная | Значение / назначение |
| --- | --- |
| `DATABASE_URL` | Строка подключения к PostgreSQL; обязательна для API, мигратора и тестов |
| `DATABASE_SCHEMA` | `public` по умолчанию; имя из строчных латинских букв, цифр и `_`, до 63 символов, начинается с буквы или `_` |
| `DOCKER_DATABASE_URL` | Строка подключения внутри Compose, с хостом `postgres` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Первичная настройка локального контейнера PostgreSQL |

`setup-local-postgres.mjs` создаёт случайный локальный пароль; секреты не
попадают в Git и Docker-образ. Для внешней PostgreSQL задайте `DATABASE_URL`
и используйте доверенный TLS-сертификат. При запуске автоматически создаётся
схема приложения; пользователь БД должен иметь права на её создание и таблицы.
После инициализации Docker-тома изменение `POSTGRES_PASSWORD` в `.env` само
по себе не меняет пароль уже существующей роли PostgreSQL.

Все операции с БД асинхронные. Запись результата, уведомления и удаление
намерения очистки выполняются в одной транзакции на одном соединении.
Поиск, фильтрация и пагинация заданий выполняются в PostgreSQL.
При потере соединения, удерживающего блокировку очереди, процесс останавливается
с ошибкой; Docker Compose перезапускает его и восстанавливает обработку после
возвращения PostgreSQL. При локальном запуске API нужно запустить снова.

## Конфигурация S3

| Переменная | Значение / назначение |
| --- | --- |
| `S3_ENDPOINT` | Локально `http://127.0.0.1:9000`; в Compose `http://s3:8333`; для AWS не задавать |
| `S3_REGION` | `us-east-1` по умолчанию |
| `S3_BUCKET` | `reports` по умолчанию; бакет должен существовать |
| `S3_PREFIX` | `reports/`; пространство ключей приложения |
| `S3_FORCE_PATH_STYLE` | `true` для локального S3; для AWS обычно `false` |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Явные ключи; задаются только вместе |
| `S3_PART_SIZE_MIB` | `8`; допустимо 5–64 МиБ |
| `S3_UPLOAD_CONCURRENCY` | `2`; допустимо 1–8; увеличение повышает расход памяти |

Если явные S3-ключи отсутствуют, используется стандартная цепочка credentials
AWS SDK: workload role, AWS profile или `AWS_*` переменные, включая временный
session token. Для подключения к внешнему хранилищу задайте конфигурацию через
окружение; не переносите локальные сгенерированные ключи в production.

Runtime нужны чтение/запись/удаление объектов, multipart-операции и проверка
доступности бакета. Создание бакета и изменение lifecycle выполняет отдельный
`node --env-file=.env scripts/init-s3.mjs`. Для локального S3 используйте
`npm run s3:up`; скрипт локальной настройки намеренно отказывается изменять
конфигурацию, уже направленную на внешний endpoint.

Прочие параметры: `MAX_PERIOD_DAYS=31`,
`RETENTION_DAYS=7`, `SEED_DEMO=true`, `API_PORT=3001`, `WEB_PORT=4200`.
В production-режиме HTTP-порт задаётся `PORT`, адрес — `HOST`.

## Проверки

```bash
npm test            # PostgreSQL: сервер, миграция; S3 заменён тестовым адаптером
npm run test:s3     # реальный S3: Excel, multipart, отмена и очистка
npm run test:e2e    # браузерные сценарии с настоящим S3
```

Перед проверками выполните `npm run infra:up`. Тесты используют настоящую PostgreSQL
со случайными отдельными схемами; интеграционные и браузерные проверки также
используют отдельные префиксы S3. Очистка затрагивает только данные своего прогона.
Браузерные тесты используют порты 4310/4311. При аварийном прерывании самого
тестового runner его схема и префикс могут потребовать ручной очистки.

Для браузерных проверок используется `/usr/bin/chromium`, если он установлен.
В другом окружении выполните `npx playwright install chromium` либо задайте
`CHROMIUM_PATH`. Артефакты неудачных проверок находятся в `test-results/`.

## Данные и границы реализации

Доступны шесть отчётов, двухшаговый мастер, поиск, фильтры, страницы, карточки
состояний и уведомления. Свод операций запускается только **00:00–06:00 МСК**;
точное начало зависит от очереди. Период ограничен 31 днём включительно.

`server/fixtures/*.json` содержит ответы октября–ноября 2026 года. Строки
фильтруются по периоду, подразделению и лицевому счёту. Для остатков выбирается
последний снимок не позднее указанной даты. За период без данных создаётся
корректный Excel с заголовками. Размер и количество строк соответствуют
реальному файлу, а не демонстрационным цифрам макета.

Сервис рассчитан на **одного демонстрационного пользователя**, без авторизации
и интеграции с настоящим ЛК. На одну схему PostgreSQL допускается один backend;
это обеспечивается advisory lock на время работы сервиса. Отдельные схемы
изолируют тесты и независимые установки. SQL-запросы используют параметры,
JSONB для структурированных данных и TIMESTAMPTZ для временных меток.
Для внедрения потребуются интеграция учётной записи/прав и настоящий адаптер БД.
Исходный чат по ссылке был недоступен; реализованы сценарии присланных макетов.

Основные модули: `src/app/` — UI; `server/service.mjs` — очередь/метаданные;
`server/workbook.mjs` — потоковый XLSX; `server/s3-storage.mjs` — S3;
`server/mock-source.mjs` — адаптер данных; `server/index.mjs` — HTTP API.

API сохраняется: `/api/catalog`, `/api/jobs`, `/api/jobs/:id`,
`/api/jobs/:id/download`, `/api/notifications`, `/api/notifications/read`.
`/api/health` проверяет процесс, `/api/ready` — также доступность PostgreSQL и S3.
Даты параметров — `YYYY-MM-DD`, временные метки — ISO UTC, отображение — МСК.

В облачных задачах используйте существующий checkout `/workspace/report-serv`:
задачи изолированы, отдельный worktree не требуется.
